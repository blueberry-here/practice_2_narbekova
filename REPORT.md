- **Причина:** флаг `--without` исключает указанные группы из процесса установки, оставляя только базовые зависимости из `[tool.poetry.dependencies]`.
**Вариант 2: `poetry install --only test`**
- **Установлены:** только группа `test` (`pytest` и его зависимости, всего 6 пакетов).
- **`pytest`:** доступен (версия 9.2.0).

- **Причина:** флаг `--only` устанавливает *исключительно* указанную группу, полностью игнорируя основные зависимости из `[tool.poetry.dependencies]`.
**Вариант 3: `poetry install` (полное окружение)**
- **Установлены:** все группы (основные зависимости + `test` + `dev`).
- **`pytest`:** доступен (версия 9.2.0).

- **Скрипт запускается:** да, успешно создал `temperature_24h.csv` и `temperature_24h.png`.
- **Тесты проходят:** да (`1 passed`).
- **Причина:** команда `poetry install` без дополнительных флагов устанавливает все зависимости, описанные в `pyproject.toml`, обеспечивая полноценное рабочее окружение для разработки и тестирования.

### 9. Lock-файл и обновление зависимости
- **Действие:** Для демонстрации работы lock-файла версия `requests` в `pyproject.toml` была временно изменена на `2.31.0`, выполнена команда `poetry lock`, после чего версия возвращена к `^2.34.2` и выполнена команда `poetry update requests`.
- **Что изменилось:** В файле `poetry.lock` обновились номера версий и контрольные суммы (хеши) для пакета `requests` и его транзитивных зависимостей. Сам файл `pyproject.toml` в итоге остался с правилом `^2.34.2`.
- **Почему это важно:** Файл `poetry.lock` гарантирует **воспроизводимость окружения**. Он жёстко фиксирует точные версии всех пакетов (включая транзитивные), которые были установлены на момент разработки. Это гарантирует, что любой другой разработчик, склонировавший репозиторий и выполнивший `poetry install`, получит абсолютно те же версии библиотек, что предотвращает ошибки типа "у меня работает, а у тебя нет" из-за выхода новых, возможно, несовместимых версий зависимостей.

### 10. Экспорт и чистое восстановление
- **Экспорт:** Установлен плагин `poetry-plugin-export`. Выполнена команда `poetry export --without-hashes --format=requirements.txt --output=requirements_poetry.txt`. Создан файл, совместимый со стандартным менеджером `pip`.
- **Восстановление:** Окружение `.venv` было удалено и создано заново стандартной командой `py -3.12 -m venv .venv`. Зависимости установлены через `pip install -r requirements_poetry.txt`.
- **Результат:** Скрипт `python plt_temp.py` успешно запускается и создаёт CSV и PNG. Это доказывает, что проект, управляемый Poetry, легко переносится на стандартные инструменты экосистемы Python.

## Сравнение подходов

### `venv + pip` (Часть 1)

**Плюсы:**
- **Простота и понятность:** Минимум инструментов, команды интуитивны (`pip install`, `pip freeze`).
- **Стандартный подход:** Работает "из коробки" с любым Python, не требует установки дополнительных инструментов.
- **Прямой контроль:** Ты сама решаешь, какие пакеты устанавливать, и видишь их точный список в `requirements.txt`.

**Минусы:**
- **Ручное управление зависимостями:** Нужно самому следить за версиями, обновлять `requirements.txt` после установки каждого пакета.
- **Нет группировки:** Все зависимости (основные, тестовые, dev) свалены в один файл, что усложняет развёртывание на продакшене.
- **Нет гарантии воспроизводимости:** `requirements.txt` с версиями вроде `requests==2.34.2` фиксирует только прямые зависимости, но не транзитивные. У другого разработчика могут установиться другие версии подзависимостей.
- **Нет удобного экспорта:** Чтобы получить список всех пакетов, нужно использовать `pip freeze`, который выводит вообще всё, включая системные пакеты.

### `Poetry` (Часть 2)

**Плюсы:**
- **Единый инструмент:** Poetry сам управляет виртуальным окружением, установкой пакетов и фиксацией версий.
- **Чёткая структура зависимостей:** Разделение на основные, тестовые и dev-группы позволяет гибко настраивать окружение под разные задачи (например, на сервере установить только основные).
- **Воспроизводимость:** Файл `poetry.lock` фиксирует точные версии **всех** пакетов (включая транзитивные), что гарантирует идентичное окружение у всех разработчиков.
- **Удобное управление версиями:** Можно указывать диапазоны версий (`^2.34.2`), и Poetry сам найдёт подходящую, при этом зафиксировав точную версию в lock-файле.
- **Экспорт в стандартный формат:** Проект легко переносится на `pip` через `poetry export`.

**Минусы:**
- **Требует установки:** Нужно отдельно устанавливать Poetry.
- **Сложнее для новичков:** Больше команд и концепций (группы, lock-файл, `pyproject.toml`).
- **Избыточен для простых скриптов:** Если проект — это один файл с парой зависимостей, Poetry может быть overkill.

### Итог

Для **учебных проектов и небольших скриптов** (как `plt_temp.py`) вполне достаточно `venv + pip` — это быстро и просто.

Для **серьёзной разработки, командной работы и production-проектов** Poetry предпочтительнее: он обеспечивает воспроизводимость, чистую структуру зависимостей и удобство сопровождения. Разница особенно заметна, когда в проекте больше 5-10 зависимостей и несколько разработчиков.
